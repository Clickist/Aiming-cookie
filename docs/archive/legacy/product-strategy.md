# 产品战略：webapp 分阶段开放能力

## 核心决策

**一个产品**（Aiming Cookie webapp），分阶段开放分析能力。当前 scope 是 flicking（详见 `docs/superpowers/specs/2026-07-05-tracking-coach-design.md` 的 scope 审视）；tracking 分析代码保留但理论待重构；手部摄像头是未来扩展（不是平行产品线）。变现方向：会员订阅 / 外设佣金（用户先免费用起来，再分阶段引入付费能力）。

详见 webapp 设计 spec：`docs/superpowers/specs/2026-07-05-flicking-coach-webapp-design.md`。

---

## Phase 1（当前）：flicking MVP

- 上传 mp4 + KovaaK's Stats CSV → 异步分析 → 诊断 + 处方 + LLM 讲解
- flicking 公平指标（`decel_frac` / `sparc` / `linearity` / `throughput` 等）
- 单次诊断 + 结果历史持久化
- **链路**：打完 → 上传 mp4+csv → 等待 → 看结果（3 步）
- 实现状态：Phase 1A-3 完成（worker 接 analyze_flicking_fair_summary + dashboard 删除 + agent loop + tracking v1 + 4 屏 dark 前端 + coach chat）

## Phase 2-3（后续）

### Phase 2：多 session + ④ 训练计划 + 趋势
- 历史聚合 → `build_progress_report` → 进步趋势 + ④ 渐进式训练计划
- 支持更多 flicking 场景

### Phase 3：tracking 接通 + 商业化
- tracking coach v1 重构（基于 accuracy / loss_count / off_time / avg_error，spec 已落）→ 接进 webapp
- 商业化：订阅（点点包 LLM key）或免费 + 用户自带 key
- **绕过 ICP 备案**（持续境外部署 + Cloudflare；见 PRD §5.2 / §9.1）——不迁国内

## 已知限制（Phase 1）

- 纯录像无法检测 miss 的点击（画面零反馈）
- flicking 分析只能覆盖命中样本，有幸存者偏差
- 需要在 UI 里明确标注这个限制

## 未来扩展：手部摄像头 + 本地采集（远期，不并入当前 MVP）

后台采集鼠标事件 + 屏幕录制 + 手部摄像头——能提供录像拿不到的数据（见下方"手部摄像头价值"），但门槛最高，**Phase 1-3 都不依赖它**。`analysis.py` 里的 PTC 命名误导问题（不是直接测肌肉张力）也是这一阶段才能用摄像头验证解决，详见 tracking-coach spec §2.1 / §6.4。

### 手部摄像头的价值（远期）

能提供的数据是其他方式拿不到的：
- 握鼠标时手指的紧张程度
- 手腕 vs 手臂的运动比例
- 点击时手指的发力模式
- 紧张时的微颤动

### 手部数据的延伸价值

**运动科学分析**（市场上几乎没有竞品）：
- 疲劳检测——连续训练后手部微颤幅度增加，建议休息节奏
- 握姿识别——抓握/指握/掌握，不同握姿对应不同训练方法
- 发力模式——手腕主导 vs 手臂主导，和 DPI/灵敏度设置直接相关
- 肌肉代偿——异常动作模式可能说明某块肌肉过度紧张，给出拉伸/放松建议

**外设推荐 + 联盟佣金**：见下方"商业化：数据驱动的外设推荐"。

## 本地采集技术方案（远期）

```
后台采集服务（Electron/Tauri）
├── 鼠标事件 — pynput（事件驱动，几乎零开销）
├── 屏幕录制 — mss/DXGI 硬件编码（CPU <5%）
├── 手部摄像头（可选）— OpenCV + MediaPipe（30fps 降分辨率）
└── 时间戳对齐 + 数据打包 + 本地存储/上传
```

三者对游戏帧率影响估计 <3%。

## 商业化：数据驱动的外设推荐（远期，Phase 3+）

不是广告，是诊断结果直接导向的产品推荐。用户看到"你的握力过大是因为鼠标太重"比看到广告有说服力得多。转化率高，且可通过联盟佣金变现。

| 诊断信号 | 来源 | 推荐 |
|---|---|---|
| 手大 + 指握 | 手部（远期）| 大鼠（G502、DA V3） |
| 手小 + 掌握 | 手部（远期）| 小鼠（Viper Mini、GPX） |
| 手腕主导 + 高 DPI | 手部 + 配置 | 控制型（涩）鼠标垫 |
| 手臂主导 + 低 DPI | 手部 + 配置 | 速度型（滑）鼠标垫 |
| 检测到握力过大 | 手部（远期）| 轻量化鼠标 + 防滑贴 |
| 减速段过冲多 | flicking | 灵敏度可能偏高或鼠标偏重 |
| 微颤随训练增加 | 手部（远期）| 建议休息节奏，可推人体工学配件 |
| 腕部过度尺偏 | 手部（远期）| 人体工学鼠标或鼠标垫高度调整 |

### 协同价值（远期，手部 + 录像分析）

- **交叉验证**：减速段 SPARC 偏低时手部摄像头是否同步检测到握力增大 → 验证而非推测
- **因果推断**：flick 过冲 → 同一时刻手部显示关节过度伸展 → "过冲是因为握力过大"
- **预测**：手部微颤幅度增加 → 接下来的 flicking 表现是否下降
- **闭环建议**：不仅说"你紧张了"，而是说"你紧张了，而且你的握姿是抓握，换个轻量化小鼠会缓解"

> 注：早期版本曾把 PTC 作为"肌肉张力系数"挂在协同价值上。**已修正**——PTC 实为 miss-frame 加速度-误差密度（详见 tracking-coach spec §2.1），不直接测肌肉张力，故"PTC 高时手在抖"的验证路径不成立；正确的协同信号应基于 flicking SPARC 等公平指标 + 手部摄像头。

## 架构分层

```
数据采集层（游戏无关）
├── 录像分析（CV）→ 目标位置、视角平移轨迹
├── KovaaK's Stats CSV → 击杀时间戳、命中/miss、TTK、元数据
├── 鼠标事件捕获（远期）→ 点击时间戳、准星移动轨迹
└── （可选/远期）手部摄像头 → 手部姿态、握力分析

分析引擎层（场景无关）
├── flicking 分析（主线）→ 减速段质量、SPARC、submovement、throughput、miss 率
├── tracking 分析（早期，待 v1 重构）→ accuracy、loss_count、off_time（PTC/J-E/TBR 已弃）
├── 手部分析（远期）→ 握姿识别、腕部偏转、微颤检测、运动模式
└── 协同分析（远期）→ 多模态交叉验证、因果推断、闭环建议

展示层
└── webapp frontend（Next.js + Tailwind，Cursor 风设计系统）
```

数据采集层可以有多种来源，分析引擎层对数据格式做抽象，不绑死任何一种采集方式。这样以后加新游戏支持只需要加一个新的采集器，分析逻辑不用改。
